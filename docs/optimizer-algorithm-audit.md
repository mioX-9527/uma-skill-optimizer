## 0. 先看结论

| 项 | 结论 |
|---|---|
| 引擎是不是随机模拟？ | **不是**。`src/` 内没有任何 `Math.random`／种子。`simulate()` 是全确定的帧级积分。所谓"1616 次模拟"= 1616 次**确定性**求解，不是 1616 场随机比赛。§B-2 |
| 优化的目标到底是什么？ | 最小化**期望完赛时间**（秒），换算成"马身"只用于展示（`× 末脚目标速度 / 2.5`）。不是胜率、不是名次。§B-6 |
| 现有搜索离穷举最优差多远？ | 13 个小规模实例：动态贪心平均差 **0.078 马身**、最差 **0.281**；跑完全部精修阶段后平均差 **0.039**、最差仍 **0.281**，13 个里 **10 个**命中最优。§E-1 |
| 后面那几步精修值不值？ | 在 plan_v2（44 候选/2034pt）真实规模下，四个精修阶段加起来 **+0.000 马身**，多花 **363 次模拟（+38%）**。其中一个阶段（多换一）在 13 个小实例里 **一次都没兑现**。§E-1 |
| 最该补什么？ | **2 出 1 入邻域**。补上后 k=10 的 9 个实例合计缺口从 0.220 → 0.042 马身，且模拟次数只有现在的 **1/3**。§E-3 |
| 什么不要做？ | 2 出 2 入（0 收益、sims 翻倍）、大规模多起点（k=10 无额外收益、sims 涨 4~6 倍）、模拟缓存（只省 22%，先做更要紧的）。§E-3 |
| 有没有确认的正确性 bug？ | 两处：`swapHintOf` 把两种不同口径的统计量直接相减（用户可见的建议文字可能失实）；`maxSims` 给小了是**抛异常**而不是降级返回。§B-1 / §B-7 |

## A. 现有算法流程图与关键函数说明

### A.1 总体流程

```
输入: course / runner / candidates(id+pt+requires+evolvesTo) / budget
  │
  ├─① 候选池解析            optimizer.ts:415-464  → Cand[]
  │     ├─ 查库去重、解析购买前置 requires、解析进化候选
  │     └─ 补双圈 ◎:451-492(◎ 价格按单圈折扣率推算)
  │
  ├─② 剔除本配置无效候选     optimizer.ts:516-528  (unsupported precision / 非常时被动 / 装配限制)
  │
  ├─③ 空手基线               optimizer.ts:531  baseSim = sim([])      ← 单次确定模拟
  │
  ├─④ 单项收益               optimizer.ts:532-561
  │     soloSec = baseSim.finishTimeSec − simExpected(withSkills)     ← 期望口径
  │
  ├─⑤ 动态贪心 greedyFill    optimizer.ts:605-628
  │     排序公式: ratio = 边际秒数 / 增量花销(costIn)   取 max
  │     装入一个后重算全部候选边际;边际 ≤ eps 的全部**永久**标 no-gain
  │
  ├─⑥ 1换1交换               optimizer.ts:633-664   SWAP_ROUNDS=10, 换入候选只取 lastMarginal 前 50
  │     每轮找「全局最优的一次交换」并落一次,然后回头重跑 ⑤
  │
  ├─⑦ 花完剩余预算 spendDown optimizer.ts:671-692   两轮:先收 >eps 的,再收 ≥−eps 的(标 filler)
  │
  ├─⑧ 期望口径复核 polish    optimizer.ts:700-732   2 轮;换出候选=最弱2个,换入候选=lastMarginal 前6
  │
  ├─⑨ 多换一 groupSwap       optimizer.ts:737-773   2 轮;换出=最弱2个∪最贵1个,换入≤3个;用期望口径
  │
  └─⑩ 汇报                   optimizer.ts:781-1007
        finalMarginals = leave-one-out(期望口径)
        totalBody = (baseSim.finishTimeSec − finalSim.finishTimeSec) × (finalSim.spurtTargetSpeed / 2.5)
```

### A.2 关键函数逐一说明（行号为当前文件）

| 问题 | 答案 | 位置 |
|---|---|---|
| **单技能收益怎么算** | `soloSec = baseSim.finishTimeSec − simExpected(withSkills)`。`withSkills` = 自己（或进化后的形态）+ 未购买的前置。多条进化方向时逐个算一遍取 max（`evoSecs`），其余列出来给用户对比。 | `optimizer.ts:532-561` |
| **空手基线怎么算** | `baseSim = sim([])`，一次不带 `positionOverrides` 的确定模拟。 | `optimizer.ts:531` |
| **集内边际怎么算** | leave-one-out：对每个已选技能，用**期望口径**模拟"去掉它"，差值就是 `finalMarginalSec`。 | `optimizer.ts:782-788` |
| **PT 约束** | `costOf(item, chosenIds)`：`requires` 已在组合里则付差额 `pt − requiresPt`；◎ 未买 ○ 则把 ○ 的价一起算。`totalSpent(set)` 与装入顺序无关。可行性判据统一是 `totalSpent(next) + cost(新增) ≤ budget`（⑥⑦ 都按"换完之后的真实总额"判，注释里记录了早先用 `remaining()+a.pt` 导致超支 62pt 的坑）。 | `optimizer.ts:495-502`、`591-602`、`649-651` |
| **互斥** | `combine()` 按 skill id 去重；`CIRCLE_BASE` 表把"买了 ◎ 就删 ○"落成替换；进化只取一个方向（`evolved`），不存在两个方向同时生效。 | `optimizer.ts:570-578`、`data.ts:52-56` |
| **前置料理** | 两个层面：① 购买层的前置（金技能的价格已含下位白，`requiresPt` 抵扣）；② **发动前提**（prereq），在模拟里按帧判定：`prereqSatisfied` 看已发动计数 / 指定技能是否已发动 / 是否第一段。 | `engine/prereq.ts:48-73`、`engine/simulate.ts:175-188` |
| **技能等级** | ○/◎ 占同一格，◎ 是替换不是叠加；◎ 价格看不到，用同格折扣率从 ○ 的实付价反推（`upPt × ○实价 / ○基准价`），比例离谱（OCR 读错）时回落基准价。 | `optimizer.ts:471-492` |
| **贪心排序公式** | `ratio = gain / cost`：`gain` = 相对**当前组合**的边际完赛时间收益（秒），`cost` = `costIn`（增量花销）。取 ratio 最大者；`cost==0` 时记 `+Infinity`（白送优先）。 | `optimizer.ts:605-628` |
| **1 换 1 搜索范围** | 换出 = 全部已选；换入 = 池子里 `lastMarginal` 前 **50** 个。每轮取**全局最优**交换（不是 first-improvement），最多 10 轮。 | `optimizer.ts:633-664` |
| **交换（swap）= 1 换 1** | 同上，没有独立的"2 换 2/2 换 1"。 | 同上 |
| **多换一搜索范围** | 换出 = 最弱 2 个 ∪ 最贵 1 个（≤3）；换入 = 池子里 `lastMarginal` 前 **5** 个的所有 1/2/3 元子集（=25 个）。最多 2 轮，用**期望口径**。注意方向是"**换出一个贵的，换进来 1~3 个便宜的**"，反过来（换出多个、换进一个）没有。 | `optimizer.ts:737-773` |
| **是否只接受立即提升** | 是，全部是。⑤ `gain > eps`；⑥⑦ `gain > eps`（⑦ 第二轮放宽到 `≥ −eps`，会把收益≈0 的"凑数技能"也装上，标 `filler`）；⑧⑨ `delta > eps`。**没有任何一种"接受变差以求跳出局部最优"的机制**（无模拟退火、无 tabu、无重启）。 | 各处 |
| **随机种子 / 场景** | **没有**。随机取位技能不抽样，而是**确定性地取点**：搜索时用区段中点 1 次（`simSearch`），汇报时在同一分位 u 上取 12 个等距点求均值（`simExpected`）。`START_DELAY_EXPECTED=0.05s` 是常数。 | `optimizer.ts:377-403`、`constants.ts:14` |
| **最终输出的指标** | `totalBody = (1800m 基准空手时间 − 最终组合期望时间) × finalSim.spurtTargetSpeed / 2.5`。即「**期望完赛时间收益**」乘一个换算常数。另有 `sumSoloBody`（各单项之和）与之前各部门以及冲突产品产品之和带来的相互作用。 | `optimizer.ts:993-1000` |

### A.3 两个口径的定义（后面会反复用到）

- **口径 A（产品口径）** `simExpected`：所有参与组合的随机取位技能，在**同一个分位 u** 上同时取点，12 个等距点求均值 → 完全相关的积分方案。
- **口径 S（搜索口径）** `simSearch`：所有随机取位技能固定在自己区段的**中点**，只跑 1 次。
- **口径 B（独立复核口径，本审计新增）**：各随机技能**独立**拉丁超立方抽样（与 `src/analysis/ablate.ts` 同法），用来检验口径 A 的结论是不是只在某种相关结构下成立。

### B.3 待确认（不敢下结论）

- **C1**：FPS/DT 是否与实际游戏一致（`DT = 1/FPS`），帧步长会不会影响"最快 − 次快"的名次差值——本次只用一个赛道/一个马娘配置，未做灵敏度测试。
- **C2**：全开冲刺、耐力对决、脚色充分三条前提机制建模（`simulate.ts:128-137`）对技能相对排序的影响未测——所有结论都在"这三个默认开启"的前提下成立。
- **C3**：目标是"期望完赛时间"，但对用户实际想赢的比赛，**胜率 / 名次分布可能给出不同的推荐**（见 §B-6）。没有拮抗样本可以验证。
- **C4**：◎ 价格的折扣率推算（`optimizer.ts:471-492`）在 OCR 读错时的兜底是否够保守，未测。

### B.4 逐条回答第"二阶段"的六个风险

1. **收益计算是否一致** — 基线/单项/总收益都用「口径 A 对口径 A」或「确定情况对确定情况」，这部分**是一致的**；不一致的是「搜索用 S、汇报用 A」（P6）和「A 本身是相关积分、与参考实现不同」（P7）。另外已确认代码里**没有**把集内边际相加当总收益的地方（注释 `optimizer.ts:154-156` 明确说单项之和与总收益的差就是交互项，并同时展示）。
2. **随机模拟是否存在误差** — **这个前提不成立**：没有随机。1616 次 = 1616 次确定求解。因此"尝试越多越容易选中随机高估方案"这种多重比较偏差**不存在**；真正的风险是"优化目标和汇报目标不是同一个"（P6），以及"期望估计器本身的积分方案可能偏"（P7）。
3. **贪心是否局部最优** — 是，且实测量化了：单个贪心 13 个实例只命中 5 个最优；后续邻域补回 5 个；剩 3 个里 2 个靠 2 出 1 入能补回。
4. **PT 和约束是否正确** — ⑥⑦的可行性判定已按"换完之后重新算总额"处理（注释里有超支 bug 的修复记录）；◎ 与下位白的处理经 `model.ts` 复刻校验（`口径一致性检查 OK` 在全部 13 个实例上通过，即我独立实现的计费/互斥规则与 `optimize` 汇报的 `finalSec` 精确一致到 1e-9）。未发现重复计费。
5. **是否存在重复计算** — 有，22%（P5），且缓存键可以很干净地定义（技能 id 序列 + 随机位置覆盖），因为引擎是确定的。
6. **是否真正优化目标** — 优化期望完赛时间。用户想赢比赛，真正关心的通常是**胜率**；两者只在同一对手阵容、同一随机环境下单调相关。举个可能出现的分歧：一个把"落后时加速"的技能会明显提升期望时间，但对胜率提升有限；一个终盘的稳定性效果反之。当前还没有拮抗样本，故标记为 C3 待确认。

### B.5 专项：价格口径的实测结论（金/下位白 与 双圈 ◎）

**原则（用户 2026-10-27 指出）**：UI 上读到的实付价就是这一把要付的钱，直接用；
**原价不参与决策**。全项目里唯一需要"推算"价格的只有双圈 ◎ —— 列表上永远只显示当前能买的那一级，看不到 ◎。

实测（`tools/bench/chain-sens.ts`，plan_v2）：

| 扫什么 | 跨度 | 结果 |
|---|---|---|
| 「巅峰之梦」（金）的实付价 | 不扫 | 它是 UI 上直接读的，不会错 |
| 「背负信念」（下位白）的实付价 | **100 → 300pt** | 巅峰之梦 **始终在名单里**，总收益一次没变（10.497 马身） |
| 预算受限（300/340/400/500/700）下扫白的实付价 | 100 / 180 / 260pt | 金的上榜情况**不变**；变的是"白自己要不要单独买"（白 100pt 时被买、180pt 时不买，总收益差 **0.11~0.265 马身**） |
| 「跟前弯道○」的实付价（◎ 由它推算） | ±40pt | 总收益在 **10.412 ~ 10.657 马身**之间摆动，推荐组合跟着变 |

**为什么扫白的价格不会影响金**：两条路径的总账恒等于金的实付价 ——
- 直接买金：账上 320（白被自动带走，不单独计价）
- 先买白再买金：白付 180 + 金再付 (320−180) = **320**

所以「下位白的价格导致金落榜」这条路径**不成立**（`optimizer.ts:495-502` 的 `Math.max(0, ...)` 只是防负数）。
白的价格真正影响的只有"白自己该不该单独买"。

**结论：用户担心的那个方向没问题，真正会咬人的是 ◎。**

### C.2 方法论要点（这些决定了数字可信不可信）

1. **穷举是真穷举**：遍历 2^k 个子集，逐个用 `totalSpent` 判可行性、`combine` 建技能集合、`口径 A` 评估。
2. **复刻校验是硬门槛**：`bench.ts` 每个实例都会断言「我复刻的计费/互斥/收益算法算出的时间 == `optimize` 汇报的 `finalSec`」，13/13 输出 `OK`；`proposal.ts` 每个实例断言「我复刻的动态贪心 == `optimize` 的 L0 组合」，13/13 输出 `一致`。**不通过就不许用这些数字**（第一次跑 proposal 时复刻不一致，我就是把脚本改到一致才继续的）。
3. **所有比较都用同一个目标（口径 A）**，即使被比较的算法内部用的是口径 S —— 这样隔离出"搜索质量"，不受估计器差异污染。
4. **独立复核用口径 B**（各技能独立 LHS）：重新给最终候选组合打一次分，看它在另一种随机结构下是否还是最优。
5. **成本按真实计数**：每个方案报的是它自己实际跑的模拟次数和墙钟毫秒，不是估算。

### C.3 验收标准（建议写进 CI）

## D. 优化建议（按优先级）

判断依据一律是 §E 的实测，**"预期收益"写的是实测数字，不是估计**。

### 优先级 1：补「2 出 1 入」邻域 ★即刻做

- **实测收益**：13 个实例中 3 个漏掉最优，其中 2 个就是被它补回来的（+0.194、+0.026 马身）；k=12 的一个实例再拿 +0.177。k=10 合计缺口 **0.220 → 0.042 马身**。
- **实测成本**：它的总搜索开销（约 166 次模拟）是现在整套流水线（约 463 次）的 **1/3** —— 加上它反而更便宜。
- **实现成本**：低。约 30 行，插在现有交换循环后面即可；就能直接复用现有的"换完之后重新算总花费"的判据。
- **验证**：`bench.ts` 的 9 个 k=10 实例应达到**穷举最优 9/9 中的 8 个**（剩 1 个要靠下面的第 4 项）；不得有任何实例倒退。

### 优先级 2：删掉/重构 `多换一`（⑨） ★做的收益是"净赚时间"

- **实测收益**：13 个小实例 + plan_v2 真实规模上，**一次都没兑现**（0/13 + 0.000 马身）；而它一个人就吃掉 **240 次模拟（37% 左右）**，因为用的是期望口径（每个组合 12 次）。
- **建议**：若要保留能力，改成「1 出 2~3 入」用**口径 S** 先筛、命中的再用口径 A 确认（同 ⑧ 的思路）；不要直接删掉——它在更大预算/便宜白技能多的时候理论上仍有价值，但目前没有证据支持继续按现在的预算跑。
- **验证**：`fullrun.ts` 的阶段阶梯上，去掉它后 `plan_v2` 的收益不得下降。

### 优先级 3：统一口径 ★正确性优先

- **做什么**：`swapHintOf`（`optimizer.ts:819-820`）里把 `simSearch(...)` 改成 `simExpected(...)`，或者至少先用 S 筛、再用 A 确认。
- **预期收益**：消灭一类用户可见失真。实测当前组合上混口径偏 0.011 马身，但同口径偏差的最大观测值是 0.196 马身——属于"现在没出事但迟早出事"。
- **兼任修正 C7**：顺手把口径 A 的"完全相关积分"换成和 `ablate.ts` 一致的独立 LHS（`ExpectedEvaluator.evaluateIndependent` 已经是现成实现）。
- **实现成本**：低到中。前者 5 行；后者会改变所有汇报数字，需要一个"口径切换"开关和一次全量基线重录。
- **验证**：`fullrun.ts` 第 4 项的两口径差应落到抽样半宽以内；所有黄金快照要重录并人工抽查。

### 优先级 4：保留并加强「期望口径复核」（⑧） ★别删

- **实测**：它是唯一在 k=12 那个实例上把 0.122 马身缺口补回来的阶段（也是 k=10 一处 0.042 的功臣）。有意思的是：**只加邻域而删掉 ⑧ 的方案在两个实例上反而输给现状**（8.011 vs 8.053、8.482 vs 8.525）。
- **建议**：⑧ 的搜索范围现在很窄（换出只看最弱 2 个、换入只看前 6 个），可以考虑让它跑更多轮、或把换入候选集放大 —— 这是"用对口径做最后一道检查"，性价比高于再加一个邻域。

### 优先级 5：修 `maxSims` 语义 ★健壮性

- **做什么**：`optimizer.ts:346` 改成"返回当前最优 + 加一条 note"，而不是 `throw`。
- **收益**：把一类整次求解失败变成降级结果。
- **实现成本**：3 行 + 一条回归测试。

### 优先级 6：多起点 —— **暂不实现**

- **实测**：k=10 的 9 个实例上多起点（5 个起点）**一次都没比 2 出 1 入更强**，sims 涨 4~6 倍；只在 k=12 那个最难的 gully example 上多拿了 +0.054。
- **结论**：先把 1~4 做完，再在更大规模（≥25 候选、含更多相思相姉邻居）上重测。若届时缺口仍集中在"单次贪心都进错盆地"，再引入。

### 优先级 7：模拟缓存 —— **暂不实现**

- **实测**：只省 22%（1327→1034）。
- **结论**：做完优先级 1/2 后总量本身就降下来了，缓存的绝对收益更小；且它引入了"缓存键是否覆盖全部影响因素"的长期风险（引擎一旦加入真随机就必须整套重做）。先不引入。

### 优先级 8：不用做的清单

- ❌ **2 出 2 入**：4 个 k=12 实例 + 9 个 k=10 实例，**零收益**，sims 翻倍。明确否决。
- ❌ **模拟退火 / tabu / 遗传算法**：现在没有任何证据表明瓶颈是"局部最优逃逸能力"——瓶颈是**邻域不完整**（P1）和**目标口径不一致**（P6）。先有证据再说。
- ❌ **改成优化胜率**：目标是另一个话题，且需要对手模型；先按 C3 标记为待确认，不动。

### E.5 一句话总结这些数字

> 现在这套搜索**不是被随机噪声害了**（根本没有随机），而是**被邻域缺口和双口径害了**：漏掉的 3 个最优里有 2 个只需要"2 出 1 入"，而花掉 38% 预算的后半段阶段在服务一个"我自己都验证不了的目标口径"。把 2 出 1 入补上、把多换一改为低精度预筛，可以在**更少模拟次数**下把 k=10 的合计缺口从 0.220 降到 0.042 甚至更低。

### E.6 金/白「替换」修复前后对照（2026-10-27）

改动本身三处（`src/optimizer.ts`）：
1. `withSkills` 由 `[...preSkills, evolved ?? skill]` 改为 `[evolved ?? skill]`（模拟里只装金）

预算宽裕时金技能即使按真实收益算，性价比仍在前列；预算紧张时排序变化会导致清单本身改变。
